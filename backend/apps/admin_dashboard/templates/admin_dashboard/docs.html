Getting Started

Authentication

All API requests require authentication via HTTP Basic Auth or token-based auth. Each request must include your API credentials.

HTTP Header 
Authorization: Bearer YOUR_API_KEY
Content-Type: application/json
cURL 
curl -X GET https://api.trustlayer.co.ke/api/v1/cases/ \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json"

Lifecycle Flow 
// Every case flows through these stages:

1. INTAKE      → Customer reports issue (Voice/SMS/API)
2. CONTEXT     → System assembles subscriber, billing, network data
3. DIAGNOSIS   → Root cause identified from assembled context
4. POLICY      → Action authorized based on rules and risk level
5. ACTION      → Remediation executed across enterprise systems
6. VERIFICATION → Service recovery confirmed, truth recorded

// AI understands and classifies.
// Policy Engine decides.
// Action Engine executes.
// Truth Engine records everything.
API Endpoints

Cases

Cases are the core resource. Each case represents one customer issue flowing through the System of Action lifecycle.

GET /api/v1/cases/ List all cases with status, amount, and metadata
POST /api/v1/cases/create/ Create a new case and initiate payment flow
GET /api/v1/cases/{case_id}/ Get full case detail including parties and status
Endpoint

Create a Case

Create a new case with parties, amount, and conditions. Returns a payment link for the buyer to complete payment.

POST /api/v1/cases/create/

Core Engines

Six modular engines power the System of Action. Each is testable, replaceable, and designed for operator integration.

EnginePurposeStatus
Context EngineAssembles subscriber, billing, network, device data from enterprise adapters● Running
Diagnosis EngineIdentifies root cause using rule-based and ML-powered analysis● Running
Policy EngineAuthorizes actions based on rules, risk level, and clearance● Running
Action EngineExecutes authorized remediation across enterprise systems● Running
Verification EngineConfirms service recovery and validates expected outcomes● Running
Truth EngineImmutable audit trail with SHA-256 hash chains● Running

Enterprise Adapters

Mock adapters for development. Production adapters connect to real operator systems via TM Forum and GSMA standards.

Adapter Contract 
// Every adapter implements this interface:

class SubscriberAdapter:
    def get_subscriber(id)     → Subscriber
    def get_service(id)        → Service
    def get_balance(id)        → Balance
    def get_bundle(id)         → Bundle

class BillingAdapter:
    def get_account(id)        → Account
    def get_transactions(id)   → [Transaction]
    def get_balance(id)        → Balance

class NetworkAdapter:
    def get_device(id)         → Device
    def get_network_state(id)  → NetworkState
    def get_incidents(area)    → [Incident]
    def activate_service(id)   → Result
    def verify_service(id)     → VerificationResult

// Today: MockSubscriberAdapter, MockBillingAdapter, MockNetworkAdapter
// Tomorrow: SafaricomSubscriberAdapter, TMFCustomerAdapter, CAMARADeviceAdapter

Error Handling

The API uses standard HTTP status codes. Errors return a JSON body with details.

Error Response 
{
  "error": "Invalid request",
  "details": {
    "amount": ["This field is required."],
    "parties": ["At least one party is required."]
  }
}
CodeMeaning
400Bad Request — Invalid parameters
401Unauthorized — Missing or invalid API key
403Forbidden — Insufficient permissions
404Not Found — Resource does not exist
429Rate Limited — Too many requests
500Server Error — Internal failure
