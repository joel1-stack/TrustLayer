How It Works

Every case follows the same lifecycle: intake, context assembly, diagnosis, policy check, action execution, and verification.

Lifecycle Flow 
// Every case flows through these stages:

1. INTAKE      → Customer reports issue (Voice/SMS/API)
2. CONTEXT     → System assembles subscriber, billing, network data
3. DIAGNOSIS   → Root cause identified from assembled context
4. POLICY      → Action authorized based on rules and risk level
5. ACTION      → Remediation executed across enterprise systems
6. VERIFICATION → Service recovery confirmed, truth recorded

// AI understands and classifies.
// Policy Engine decides.
// Action Engine executes.
// Truth Engine records everything.
V2 API (Operational)

Operational Endpoints

Organization-agnostic API. Create cases for any bank, telco, or e-commerce partner. The system assembles context, diagnoses, and resolves.

GET /api/v1/v2/organizations/ List all active organizations (banks, telcos, e-commerce)
GET /api/v1/v2/organizations/detect/?mcc=639&mnc=02 Detect organization by SIM card MCC/MNC codes
POST /api/v1/v2/cases/ Create a case and run full pipeline (context → diagnosis → action)
GET /api/v1/v2/cases/{case_id}/ Get case status with context, diagnosis, actions, verification
GET /api/v1/v2/cases/{case_id}/timeline/ Get state transition history for a case
POST /api/v1/v2/cases/{case_id}/feedback/ Customer confirms resolution outcome
Endpoint

Create a Case

Open a new case for a subscriber. The system assembles context, diagnoses root cause, selects an action, executes it, and verifies the outcome — all in one request.

POST /api/v1/v2/cases/

{
  "msisdn": "+254798765432",

  "channel": "API",
  "severity": "HIGH",
  "metadata": {

  }
}

Core Engines

Six modular engines power the System of Action. Each is testable, replaceable, and designed for operator integration.

EnginePurposeStatus
Context EngineAssembles subscriber, billing, network, device data from enterprise adapters● Running
Diagnosis EngineIdentifies root cause using rule-based and ML-powered analysis● Running
Policy EngineAuthorizes actions based on rules, risk level, and clearance● Running
Action EngineExecutes authorized remediation across enterprise systems● Running
Verification EngineConfirms service recovery and validates expected outcomes● Running
Truth EngineImmutable audit trail with SHA-256 hash chains● Running

Enterprise Adapters

Organization-specific adapters for each vertical. Mock adapters for development, real adapters connect to KCB, Safaricom, Equity, Airtel, Jumia systems.

Adapter Contracts 
// Every adapter implements a vertical-specific contract:

class CustomerContextAdapter:
    def get_customer(customer_id) → Customer
    def get_account(customer_id) → Account

class ServiceContextAdapter:
    def get_service(customer_id) → Service
    def get_network_state(customer_id) → NetworkState

class BillingContextAdapter:
    def get_account(customer_id) → Account
    def get_balance(customer_id) → Balance

class NetworkContextAdapter:
    def get_device(customer_id) → Device
    def get_incidents(area) → [Incident]
    def activate_service(customer_id) → Result

class FraudSignalAdapter:
    def get_fraud_signals(customer_id) → FraudSignals

class ActionAdapter:
    def execute(action_type, params) → ActionResult

// AdapterRegistry: get(slug, adapter_type) → org-specific adapter
// kcb → TelcoMockAdapters | safaricom → TelcoMockAdapters
// jumia → EcommerceMockAdapters | equity → BankingMockAdapters

Status Codes

Every case has a numeric status code indicating its position in the lifecycle.

CodeStatusCategoryDescription
10000CONTEXT_ASSEMBLYActiveCase opened, assembling service context
12000SUBMITTEDActiveCase submitted, awaiting processing
13000DIAGNOSINGActiveContext assembled, diagnosis in progress
14000ACTION_PENDINGActiveDiagnosis complete, action authorized
15000VERIFYINGActiveAction executed, verifying outcome
15500ESCALATEDActiveAutomated resolution failed, escalated to agent
18000RESOLVEDTerminalIssue verified as resolved
21000CANCELLEDTerminalCase cancelled by user or operator
22000UNRESOLVABLETerminalCase closed without resolution
24000FAILEDTerminalSystem or provider error during processing

Error Handling

The API uses standard HTTP status codes. Errors return a JSON body with details.

Error Response 
{
  "error": "Invalid request",
  "details": {
    "msisdn": ["This field is required."],
    "intent": ["At least one intent is required."]
  }
}
CodeMeaning
400Bad Request — Invalid parameters
401Unauthorized — Missing or invalid API key
403Forbidden — Insufficient permissions
404Not Found — Resource does not exist
429Rate Limited — Too many requests
500Server Error — Internal failure
